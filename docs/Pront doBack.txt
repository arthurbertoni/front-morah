## Autenticação e permissões (JWT + Spring Security)
- **Login:** `POST /auth/login` com e-mail e senha. A senha é verificada com BCrypt. Credenciais inválidas → 401.
- **Sessão:** cada login cria uma `Sessao` com: id (UUID), pessoa, perfil ativo, condomínio ativo, unidade ativa (opcional), `refreshToken` (UUID opaco) e `refreshExpiraEm` (7 dias).
- **Contexto inicial:** o primeiro `PessoaPerfil` da pessoa (menor id). `LoginResponse` traz também todos os `perfisDisponiveis`.
- **Access token:** JWT HS256 assinado com `morah.jwt.segredo` (application.yml, mínimo de 32 bytes), validade de 3600 s, com as claims `sub` (pessoaId), `sid` (id da sessão), `perfil`, `condominio_id` e `unidade_id` (omitida para síndico e portaria). `tokenType` = `"Bearer"`.
- **Validação do token:** o `JwtDecoder` valida assinatura e expiração e um `OAuth2TokenValidator` próprio confere se a sessão `sid` ainda existe. Assim o logout invalida o access token imediatamente.
- **Papéis:** um `JwtAuthenticationConverter` transforma a claim `perfil` em `ROLE_<PERFIL>`. `proprietario` recebe também `ROLE_MORADOR`, porque o contrato diz que o proprietário é cumulativo ao morador.
- **RBAC declarativo:** `@EnableMethodSecurity` e `@PreAuthorize("hasAnyRole(...)")` em cada método de controller, com exatamente os perfis listados em `security: bearerAuth: [...]` daquela operação no contrato.
- **Rotas públicas:** `/auth/login`, `/auth/refresh` e `/financeiro/webhooks/pagamentos`. Todas as outras exigem token.
- **Configuração:** sessão `STATELESS`, CSRF desabilitado, sem form login nem HTTP Basic.
- **Erros de segurança:** `AuthenticationEntryPoint` (401) e `AccessDeniedHandler` (403) próprios, respondendo `ProblemDetail` em `application/problem+json`, igual ao resto da API.
- **`POST /auth/contexto`:** se a pessoa não tiver o vínculo (condomínio, perfil) pedido → 403. Caso contrário, apaga a sessão atual e cria outra com o novo contexto.
- **`POST /auth/refresh`:** procura a sessão pelo refresh token. Se não existir ou estiver vencido → 401. Senão, apaga a sessão e cria outra com o mesmo contexto (rotação).
- **`POST /auth/logout`:** apaga a sessão do `sid` (204).
- **Contexto vem do token:** condomínio, unidade e perfil vêm SEMPRE do `UsuarioLogado`. Nunca da URL, exceto nos endpoints administrativos `/unidades/{unidadeId}` do síndico, e mesmo assim só dentro do condomínio ativo.
- **Escopo de unidade:** morador ou proprietário acessando recurso de outra unidade (cobrança, autorização de visita, reserva, encomenda) → 403.
- **Escopo de condomínio:** qualquer recurso de outro condomínio → 404.

## Módulos ativáveis
- Um `HandlerInterceptor` (`ModuloAtivoInterceptor`) mapeia o prefixo da rota para o módulo:
  - `/financeiro/**` → `financeiro` (exceto o webhook)
  - `/portaria/**` → `portaria`
  - `/avisos/**` → `avisos`
  - `/areas-comuns/**` e `/reservas/**` → `reservas`
  - `/unidades/**` → `minha_unidade`
  - `/encomendas/**` → `encomendas`
- Se o módulo estiver desativado no condomínio do token → 403 com `detail` "Módulo X desativado neste condomínio", para qualquer perfil, inclusive síndico.
- O interceptor consulta o Singleton `CacheModulosAtivos`, que é atualizado sempre que o síndico altera um módulo.
- Login, Tela Inicial, Notificações e Personalização nunca são bloqueados.
- Como as notificações continuam acessíveis, notificações já geradas por um módulo desativado continuam visíveis.

## Regras de negócio
O contrato já descreve as regras no `description` de cada operação. Resumo e detalhes de implementação:

### Financeiro
- **Status `atrasado`:** calculado na leitura (cobrança `pendente` com vencimento anterior a hoje). Não há job agendado.
- **PIX:** gateway simulado. O código é uma string fixa + id + valor, com `expiraEm` = agora + 30 min. Cobrança `pago` ou `cancelado` → 409.
- **Baixa manual:** marca a cobrança como `pago` (já paga ou cancelada → 409). Meio, data e observação não são persistidos, porque `Cobranca` não os expõe.
- **Webhook:** `X-Webhook-Signature` = HMAC-SHA256 em hexadecimal do corpo bruto, com o segredo `morah.webhook.segredo`. Assinatura inválida → 401. Receba o corpo como `String` para calcular a assinatura e converta com `ObjectMapper`. Processamento síncrono, resposta 202. Baixa manual e webhook passam pelo `ProcessamentoPagamentoTemplate` (ver Design patterns).
- **Geração em lote:** usa a Strategy `EstrategiaRateio`. Arredonde com `BigDecimal` em 2 casas (HALF_UP). Unidades com falha vão para `falhas`.
- **Inadimplência:** conforme o `description` da operação.

### Portaria
- **Expiração:** `MINUTOS_EXPIRACAO_AUTORIZACAO = 30`; o status `expirada` é calculado na leitura.
- **Status de acesso:** conforme o contrato (`no_condominio` / `saiu`).

### Avisos
- Visibilidade por público-alvo, `categoria` e `prioridade` como filtros, `LeituraAviso` (pessoa + aviso) para `lidoPeloUsuario`.
- `deletarAviso` expira o aviso (não apaga).

### Reservas
- Horários de 1 hora das 08:00 às 22:00 (constantes `HORA_ABERTURA` e `HORA_FECHAMENTO`).
- Sobreposição com reserva `confirmada` → 409.

### Minha Unidade
- Convite de inquilino pelo canal e-mail (simulado).
- Encerrar inquilino apaga o `PessoaPerfil` e as `Sessao` dele.

### Encomendas
- Código de retirada de 6 dígitos gerado pelo Singleton `GeradorCodigo`.
- Ocorrência de extravio marca a encomenda como `extraviada`.

### Personalização
- Cada condomínio tem exatamente uma `Personalizacao` (criada no seed) e uma linha de `ModuloCondominio` por valor de `ModuloCodigo`.
- `nome` do módulo é preenchido pelo servidor a partir do enum ("Financeiro", "Portaria", "Avisos", "Reservas", "Minha Unidade", "Encomendas").
- `atualizadoEm` é preenchido pelo servidor.

### Notificações
Disparadas via `NotificacaoTemplate` em:
- criar aviso
- registrar visitante e reenviar autorização
- criar encomenda
- criar reserva
- gerar cobranças e pagamento confirmado pelo webhook
- convite de inquilino

### Dashboard
- Limite de 5 itens nas listas.
- Seções de módulos desativados vêm vazias (`[]`, `0`) ou ausentes (`inadimplencia` quando o financeiro está desativado).

## Design patterns
Cada pattern deve ter um comentário curto dizendo qual problema resolve ali.

No total são **8 usos: 3 Template Method, 3 Strategy e 2 Singleton**. Não crie outros patterns além destes.

### Singleton (2 usos)
O frontend já tem dois Singletons (cliente HTTP e logger). No backend, implemente dois, mostrando as duas formas clássicas de Singleton em Java (sem depender do container do Spring):
1. **`GeradorCodigo`** (GoF clássico: construtor privado + `getInstance()` com o idiom *holder*): uma única instância de `SecureRandom`, que é cara de criar, gera os códigos de 6 dígitos de retirada de encomenda e de autorização de terceiros.
2. **`CacheModulosAtivos`** (enum Singleton, `INSTANCE`): mantém em memória um `ConcurrentHashMap<Long, Set<ModuloCodigo>>` com os módulos ativos de cada condomínio, para o `ModuloAtivoInterceptor` não ir ao banco a cada requisição. É invalidado em `alterarModulo` e carregado sob demanda.

O `TokenService` (que gera os JWT) é um `@Service` comum do Spring e NÃO deve ser apresentado como pattern.

### Template Method (3 usos)
1. **`BaseCrudController<T>`:** fluxo fixo por requisição (obter o `UsuarioLogado` → validar payload → executar → verificar escopo do recurso → responder), com os hooks `validar(input)` e `verificarEscopo(recurso, usuario)`.
   - Lança 403 ou 404 conforme as regras de escopo; o RBAC por perfil fica no `@PreAuthorize`.
   - Usado por `AvisoController` (CRUD completo), `ReservaController` e `EncomendaController`, que só expõem os métodos que o contrato tem.
2. **`NotificacaoTemplate`:** fluxo fixo (montar payload → escolher canal → enviar → registrar a `Notificacao` no banco). O envio é simulado com log.
3. **`ProcessamentoPagamentoTemplate`:** fluxo fixo para quitar uma cobrança (validar origem → localizar cobrança → verificar se pode ser paga → marcar como `pago` → notificar a unidade).
   - `BaixaManualProcessador`: na validação, exige um síndico do mesmo condomínio; cobrança paga ou cancelada → 409.
   - `WebhookPagamentoProcessador`: na validação, confere a assinatura HMAC (inválida → 401); status `falhou` encerra o fluxo sem alterar nada.
   - Os passos comuns (localizar, verificar, marcar como pago, notificar via `NotificacaoTemplate`) ficam só na classe base.

### Strategy (3 usos)
1. **`EstrategiaRateio`:** `RateioIgualitario` e `RateioFracaoIdeal`, escolhida pelo `tipoRateio` da taxa.
2. **`CanalNotificacao`:** `CanalPush` (portaria, encomenda, aviso, reserva) e `CanalEmail` (convite de inquilino e financeiro), escolhido no passo "escolher canal" do `NotificacaoTemplate`.
3. **`MontadorDashboard`:** `DashboardMoradorMontador` (morador e proprietário), `DashboardSindicoMontador` e `DashboardPortariaMontador`, escolhido pelo perfil ativo.

## Testes
Testes de integração com MockMvc usando um SQLite separado (`target/test.db`). Os testes obtêm o token chamando `POST /auth/login` de verdade com os usuários do seed. Cobrir:
- **Auth:**
  - Login válido → 200 com `accessToken`, `refreshToken` e contexto.
  - Login com senha errada → 401.
  - `/auth/me` sem token, com token adulterado ou com token expirado → 401.
  - Contexto com vínculo inexistente → 403.
  - Refresh válido → 200; refresh inválido → 401; o refresh antigo não funciona depois da rotação.
  - Logout invalida o access token (a chamada seguinte retorna 401).
- **403 por perfil:**
  - Morador criando aviso.
  - Morador gerando cobranças.
  - Portaria listando cobranças.
  - Morador registrando visitante.
  - Morador (não proprietário) cadastrando inquilino.
  - Morador alterando personalização ou módulos.
- **Proprietário cumulativo:** proprietário acessando rota de `morador` → 200.
- **Financeiro:**
  - Morador lendo cobrança de outra unidade → 403.
  - PIX de cobrança paga → 409.
  - Rateio igualitário e por fração geram os valores corretos.
  - Webhook com assinatura inválida → 401; com assinatura válida marca a cobrança como paga.
- **Portaria:**
  - Decisão em autorização já decidida → 409.
  - Decisão em autorização expirada → 409.
- **Reservas:**
  - Reserva sobreposta → 409.
  - Vistoria com dano cria ocorrência.
- **Avisos:**
  - Aviso expirado → 410.
  - GET de aviso marca como lido.
  - PATCH parcial altera só o campo enviado.
- **Encomendas:**
  - Retirada com código inválido → 409.
  - Retirada com código de terceiro válido → 200.
  - Registrar encomenda cria notificação.
- **Personalização:**
  - Cor fora do formato `#RRGGBB` → 400.
  - PATCH parcial de cores mantém os outros campos.
  - Desativar `encomendas` faz `GET /encomendas` → 403; reativar volta a 200.
  - Com `encomendas` desativado, o dashboard do morador vem com `encomendasPendentes` vazio.
- **Gerais:**
  - Paginação com `size=101` → 400.
  - Dashboard devolve o `perfil` correto para cada usuário.

Inclua também testes unitários simples de cada pattern:
- **Singletons:** `getInstance()` e `INSTANCE` devolvem sempre o mesmo objeto; o cache é invalidado.
- **Templates:** ordem dos passos nos três; no `ProcessamentoPagamentoTemplate`, o webhook com `falhou` para antes de marcar como pago.
- **Strategies:** troca de estratégia.

Não exija meta de cobertura.

## Versionamento (Git)
Repositório `morah-backend`, branch `main`, com um commit por módulo, na ordem abaixo. Cada commit traz o código do módulo, os testes dele e os dados do módulo no `data.sql`.

Regras:
- Rode `mvn clean test` antes de cada commit e só faça o commit se tudo passar.
- Nunca junte dois módulos no mesmo commit nem deixe código de um módulo futuro adiantado.
- Mensagens em português, no padrão `tipo(modulo): descrição`.
- Não versione `morah.db`, `target/` nem arquivos da IDE (crie o `.gitignore` no primeiro commit).
